# 开发与测试接入

## 1. 推荐的首次开发顺序

先用`reference/`主数据＋`seed/`关联数据完成工单列表和详情，再接入预设AI建议、人工复核与派工，最后做提醒、看板和连续对话。可直接使用`demo/demo_scenarios.json`中的ID做入口。真实产品信息和故障根因不要混用。

```javascript
// 在应用服务层读取；实际项目请替换成自己的加载机制。
const ticket = tickets.find(t => t.id === selectedId);
const product = products.find(p => p.id === ticket.product_id);
const conversation = messages.filter(m => m.ticket_id === ticket.id);
const timeline = events.filter(e => e.ticket_id === ticket.id)
  .sort((a, b) => a.at.localeCompare(b.at));
```

大数组建议只在开发服务端载入一次。多表JSON适合导入本地数据库，也可以供简单Mock服务读取。文件名不是官方接口地址。所有跨租户记录均需先做权限过滤，不能把整包客户资料送入AI。

## 2. 事实、规则、运行记录和测试答案

| 数据层 | 代表文件 | 可否用于AI输入 |
| --- | --- | --- |
| 公开事实 | `research/sources.json`、`reference/products.json` | 可以，按用途选取并附来源 |
| 演示规则 | `routing_rules.json`、`sla_policies.json`、`knowledge_base.json` | 可以，但要标明演示规则 |
| 当前授权来件 | `evaluation/inputs.jsonl`及其权限允许的上下文 | 可以 |
| 历史业务记录 | `seed/` | 只允许任务确实需要的历史记录；不得在离线分诊评测时泄漏后续结果 |
| 预期标签/示例输出 | `evaluation/expected.jsonl`、`example_agent_outputs.jsonl` | 不可以，它们只供评估或预设演示 |

`seed/tickets.json`含人工确认后的分类、状态、标签和SLA，所以不要直接把整个对象作为离线分诊输入。`inputs.jsonl`已移除这些答案字段。`authorized_context`只是演示已有授权的实体引用，应用仍要检验对应租户，不能信任客户端随意传入的ID。

## 3. 工单生命周期与人工协作

正式状态和允许跳转见`reference/workflow.json`。AI建议本身不等于状态已改变，`ai_suggestions.review`记录待确认、已接受或人工更正。只有人工批准的操作才写入分派、合并、关闭等状态事件。

`events`是每条工单的状态事件序列，工单快照的状态应与最后一条事件一致。`assignments`保留人工确认的分派证据。消息中的中文内部说明不应直接给海外客户展示；`visibility=customer`才是面向客户的内容。

等待客户资料不等于派工完成；预约提案不等于预约成功；保修申请不等于批准免费更换。备件库存只是虚构快照，不可据此操作真实仓储。

## 4. 分诊规则优先级

1. 新的安全风险优先人工升级，不等待SN补齐。
2. 确认能否判断，缺信息追问；低置信度交人工复核。
3. 按问题类别所需技能，再按设备所在地选择团队。
4. 考虑语言、人员可用性和容量；没有可用人时显示队列，不伪造派工成功。
5. 所有分派仍须人工确认。客户“很急”不能直接等同P0；否定与历史时间范围必须理解。

安全类样本中的缺失字段是待补收的非阻塞信息；`may_delay_for_missing_information=false`是关键预期。未知地区进入全球人工调度。设备联网失联不必然等于设备停机。

## 5. 固定时钟与SLA

`manifest.as_of`是静态数据的演示时刻。SLA规则：连续UTC时间、24×7、不暂停；从`clock_start_at`开始，客户可见的第一条人工回复停止首次响应计时，`resolved_at`停止当前周期的解决目标计时。首次响应和解决目标都是演示值，不是服务承诺。

判断采用严格大于：正好等于到期时刻不算超时，超过1秒算超时。取消与合并工单排除SLA统计。重开生成新的周期，`previous_cycle`保留旧周期的响应及解决结果。已解决/关闭工单如果以前超时，应保留历史超时结果。

`notifications`只表示本地待显示提醒，不会发送邮件、短信或联系任何真实人员。按`dedupe_key`避免重复提醒。看板预期在`demo/dashboard_expected.json`，不从这些模拟数字推导真实服务KPI。

## 6. 如何做测试

### 数据结构与引用

运行`validate_dataset.py`。它检查JSON结构、枚举、唯一ID、跨表关系、时间、状态回放、人工确认记录、SLA重算、来源与看板合计。`schema/contracts.json`声明每份生成数据对应哪份Schema；可在实际应用中使用标准JSON Schema引擎接入。

自带校验器只实现本包用到的Schema关键词，不是通用完整的JSON Schema引擎。校验通过只证明数据包内部一致，不代表应用实现已测试。

### 单轮Agent功能回归

逐行向你实现的分诊逻辑或AI提交`evaluation/inputs.jsonl`，把输出写到单独文件，再按`case_id`与`expected.jsonl`对照。建议分别检查：类别、优先级、团队、缺失字段集合、下一步动作、安全升级与人工审批要求。字段集合比较应忽略顺序。

`example_agent_outputs.jsonl`是格式示例，并非真实模型运行记录。不要把示例和金标一起送入模型后再称为“准确率”。对于模糊问题，可接受的同义分类需要业务定义；金标只表示本演示规则下的预期。

`splits.json`按48个场景族分组，开发320例、验证80例、测试80例。同一“问题＋上下文”组合的变体不跨组，但基础描述仍会共享。它适合防止最明显的重复泄漏，不是严格的独立真实评测集，也不建议拿全部数据训练后报告本包上的分数。

### 连续对话

`conversation_cases.json`包含客户补充信息和中间检查点。每收到新证据都重新判断；新危险迹象覆盖旧的低优先级。授权不足不能因为客户继续催促而被跳过。连续对话夹具不执行真实账号转移。

### 异常与应用行为

`fixtures/edge_cases.json`把案例分成triage、validation、workflow、sla_boundary。每例含输入和预期；`must_not`列出不得出现的行为。validation/workflow类需要你实现服务端逻辑后接入测试，当前数据包未假装已经实现了鉴权、上传、并发控制或幂等。

损坏附件夹具只提供元数据；实际应用需要构造损坏字节或模拟读取错误。正常`attachments/`都是文本，可验证路径、上传显示与关联，不能测试图像视觉能力。

## 7. 测试适用范围

适合：页面开发、筛选、分页、详情、时间线、人工更正、路由解释、提醒、复发/重复、多语言来件展示，以及AI提示词的早期功能检查。

尚需真实授权资料和业务访谈：实际故障分类、保修与责任判断、真实服务目标、跨系统写入、地区规则、模型泛化和安全处置有效性。性能压测也应单独生成负载，492条不是大规模并发样本。

## 8. 再生成与扩展

在`scripts/catalog.py`维护事实来源、产品参考、多语种基础描述与场景；在`build_dataset.py`维护关系与规则。脚本种子固定为20261024，可重复生成。改完运行生成器，再运行校验器。自己的业务扩展应放在单独目录或先备份，避免被同名生成文件覆盖。

该目录未包含应用数据库迁移脚本或特定前端框架代码；JSON结构与UI框架无关。可按未来技术选择导入，保留各实体的稳定字符串ID。
